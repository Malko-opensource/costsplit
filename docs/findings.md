# 벤치마크 결과: 무엇이 큰 모델의 코딩을 비싸게 만드나

이 문서는 2026년 11월 10~12일에 `cmd/polybench`로 잰 결과를 정리합니다. 질문은 두 가지였습니다.

1. graybox 방식(큰 모델이 구조와 요구사항을 쓰고 작은 모델이 본문을 채움)이 비용을 줄이는가.
2. 큰 모델이 토큰을 많이 쓰는 부분 중 무엇을 작은 모델이나 도구로 넘길 수 있는가.

## 요약

- **graybox 방식은 비용을 줄이지 못했습니다.** Polyglot에서 성공률 81%, 문제당 $0.11로, Opus 단독(99%, $0.049)보다 낮고 비쌌습니다. 설계 산출물이 정답 코드보다 길었습니다.
- **완전한 인수 테스트가 있으면 작은 모델로 충분합니다.** 테스트를 보여 주면 Haiku가 Polyglot 실패 45문제를 전부, SWE-bench 45문제 중 41개를 풀었습니다.
- **인수 테스트가 없을 때 그 자리를 메우는 값싼 사전 설계는 찾지 못했습니다.** 힌트, 의사코드, 기존 테스트, 이슈에서 뽑은 테스트(Haiku 작성, Opus 작성) 모두 효과가 없었습니다.
- **기존 코드 수정에서 큰 모델 비용의 80%는 파일을 읽는 데 듭니다.** Haiku가 읽고 함수를 고르고, Opus가 그 조각만 보고 짧은 지시를 쓰고, Haiku가 편집하면 비용이 64% 줄었습니다. 통과 수는 45문제 중 32개로 Opus 단독(34개)과 통계적으로 구분되지 않았습니다.
- **작은 모델로 넘기지 못한 것은 "무엇이 옳은 수정인가"의 판단입니다.** 정확한 조각을 줘도 Haiku는 40%, Opus는 68~80%였습니다.
- **읽기를 줄이는 압축은 검색형 출력에는 통하고, 코드에는 복구 경로가 필요합니다.** Haiku가 고른 부분만 남기고 토큰을 70% 줄이면, HotpotQA 근거 문장은 92%가 남았습니다. 반면 고칠 함수는 62%만 남았습니다. Opus가 개요를 보고 골라도 67%였습니다(6절). 그래도 숨긴 함수의 이름을 남긴 압축본을 Opus가 읽으면, 고칠 위치에 대한 판단은 전체를 읽을 때와 같았고(30/45 대 30/45, 일치율도 같은 조건을 두 번 돌린 잡음 수준), 비용은 53% 줄었습니다. 코드 본문이 필요할 때 숨겨져 있으면, Opus는 71%의 경우 다시 열었습니다. 나머지 대부분은 기억하고 있던 sympy 코드로 답했습니다. 보지 않은 줄을 인용하면 돌려보내는 관문을 두자 그런 답은 0개가 됐습니다(7절). 이 화면을 읽고 Opus가 직접 고치면 45문제 중 36개를 통과했습니다. Opus 단독(34개)보다 낮지 않았고, 비용은 35% 적었습니다. 편집을 Haiku에 넘기는 것은 읽기를 줄인 뒤에는 거의 이득이 없었습니다(8절). 그러나 파일을 직접 찾고 캐시를 쓰는 실제 에이전트 루프에 읽기 도구로 넣으면, 통과는 같고(34 대 33) 비용은 36% 늘었습니다. 에이전트는 Grep으로 찾은 줄만 보고 고치는 경우가 많아 원래 읽기 비용이 작았습니다. 늘어난 턴과 관문이 비용을 키웠습니다(9절). Haiku가 미리 탐색해 브리핑을 줘도 Opus는 같은 턴 수로 스스로 확인했고, 비용은 47% 늘었습니다. Haiku 단독 에이전트는 비용이 7분의 1이지만 통과가 49%로 낮았습니다(10절). 에이전트 루프에서 비용을 실제로 줄인 것은 Opus의 추론량을 낮추는 것이었습니다. `--effort low`는 비용을 32% 줄였지만 통과도 3문제 줄었습니다. Sonnet 5.5와 "Haiku 먼저, 막히면 Opus" 규칙은 Opus low보다 통과가 적고 비용은 같거나 높았습니다(11절).
- **모델이 내리는 통과 판정은 믿을 수 없습니다.** 모델이 쓴 테스트나 결정 모델로 판정하면 Polyglot에서 13%, SWE-bench에서 약 40%가 틀린 채 통과했습니다.

## 측정 조건

- 모델: 작은 모델 Haiku 5.5(`claude-haiku-5-5`), 큰 모델 Opus 5.5(`claude-opus-5-5`). `claude -p`를 도구 없이, 스키마로 JSON 출력을 강제해 호출했습니다.
- 비용: CLI가 보고한 금액입니다. 역산한 정가는 백만 토큰당 Haiku 입력 $0.10, 출력 $0.50, Opus 입력 $4, 출력 $20입니다.
- Polyglot 실험(1, 2절)은 입력 전체가 1시간 캐시 쓰기 요금(입력가의 2배)으로 청구됐습니다. SWE-bench 실험(3절 이후)은 `DISABLE_PROMPT_CACHING=1`로 캐시를 끈 정가입니다. 두 묶음의 금액은 서로 직접 비교할 수 없습니다.
- Haiku 호출 한 번의 입력이 10만 토큰을 넘은 경우는 5배로 청구됐습니다.
- 지금까지 든 비용은 약 $127입니다(6절 $3.07, 7절 $29.88, 8절 $7.01, 9절 $11.44, 10절 $8.08, 11절 $11.79 포함). 6~8절도 캐시를 끄고 쟀습니다. 9~11절만 캐시를 켰습니다.

## 1. Polyglot: graybox 방식

Aider Polyglot의 Go, Java, JavaScript, Python 169문제입니다. 단독 조건은 테스트 출력을 받아 2회까지 시도합니다. graybox 조건은 Opus가 graybox를 쓰고, Haiku가 계획과 구현을 하고, Haiku가 결정 모델 역할을 합니다(확신도 기준 0.5).

| 조건 | 통과 | 문제당 비용 |
| --- | --- | --- |
| Haiku 단독 | 124 (73.4%) | $0.0033 |
| Opus 단독 | 168 (99.4%) | $0.0490 |
| graybox | 137 (81.1%) | $0.1125 |

- graybox는 Haiku가 실패한 45문제 중 33개를 살렸습니다. 27개는 Haiku가 graybox 안에서 풀었고 6개는 Opus로 승격됐습니다.
- 반대로 Haiku가 혼자 풀던 문제 20개를 잃었습니다. 원인은 결정 모델의 오판 10개, 계획 단계 검사의 잘못된 차단 5개, 하네스 버그 4개, 통과하지 못한 graybox 1개입니다.
- 결정 모델은 통과시킨 156건 중 21건(13%)을 틀렸습니다.
- graybox 비용 $19.01 중 $17.42가 Opus였습니다. Opus의 출력은 graybox를 쓸 때 평균 1,953토큰, 같은 문제를 직접 풀 때 1,292토큰이었습니다.
- 정답 코드의 줄 수와 분기 수는 Haiku의 실패를 예측하지 못했습니다(AUC 0.47~0.56). 테스트 수와 언어가 약하게 맞았습니다(0.65 안팎).

## 4. SWE-bench: 큰 모델의 비용 분해와 두 모델 조합

Opus 단독의 문제당 비용 $0.116은 읽기 $0.092(80%), 추론 $0.010, 편집 출력 $0.014로 나뉩니다. 새 코드를 쓰는 Polyglot에서는 반대로 출력이 68%였습니다.

비싼 부분을 하나씩 넘겼을 때의 결과입니다(같은 25문제, 같은 조각).

| 단계 | 통과 | 문제당 비용 |
| --- | --- | --- |
| Opus가 파일 전체를 읽고 수정 | 17 | $0.116 |
| Haiku가 읽고 고른 함수의 조각만 Opus가 읽음 | 17 | $0.055 |
| 조각에서 파일 개요를 뺌 | 17 | $0.041 |
| Opus는 지시만 쓰고 Haiku가 편집 | 17 | $0.034 |

- 조각은 `adapters/python/slice.py`가 만듭니다. import 문, 고른 함수의 전체 소스, 그 함수가 부르는 같은 파일 안 함수가 들어갑니다. 중앙값으로 파일의 12%입니다.
- 고칠 함수를 정확히 알려 준 조각으로는 Opus가 20개, Haiku가 10개를 통과했습니다.
- 지시는 평균 57단어이고, Opus의 보이는 출력은 755토큰에서 366토큰으로 줄었습니다.

조합을 정한 뒤, 쓰지 않았던 20문제와 45문제 전체로 확인했습니다.

| 대상 | Opus 단독 | 조합 |
| --- | --- | --- |
| 새 20문제 | 17개, $0.137 | 15개, $0.057 |
| 45문제 전체, 1차 | 34개, $0.125 | 32개, $0.045 |

- 추론 토큰은 어려운 문제에서 가장 큰 비용이 될 수 있습니다. 한 문제에서 추론에만 11,000토큰($0.22)을 썼습니다.

## 5. 위치 찾기: 목록에서 고르게 하기

처음에는 Haiku에게 고칠 함수 이름을 자유 문자열로 받았습니다. 45문제 중 4문제에서 이름 뒤에 설명이 붙거나 다른 파일의 함수를 적어 조각을 만들지 못했고, 파일 전체를 보여 주게 됐습니다. 이 4문제가 조합 전체 비용의 22%였습니다.

지금은 도구가 파일의 함수 목록을 뽑고, 모델은 그 목록 안에서만 고릅니다(JSON 스키마의 `enum`). 새로 추가할 함수 이름만 자유 문자열로 받습니다. 위치 찾기만 따로 45문제에 돌린 결과입니다.

| 방식 | 파일 전체로 되돌아감 | 조각이 고쳐야 할 함수를 모두 포함 |
| --- | --- | --- |
| 자유 문자열 | 4 | 30 |
| 목록에서 고르기 | 1 | 31 |

- 유효하지 않은 답은 없어졌습니다. 남은 1건은 함수가 아닌 클래스 속성을 추가하는 61줄짜리 파일입니다.
- 어느 함수를 고르느냐의 정확도는 그대로입니다(30 대 31). 이 부분은 형식이 아니라 판단의 문제입니다.
- 이 방식으로 바꾼 뒤의 전체 조합(수정까지)은 다시 재지 않았습니다.

## 6. 읽기 압축(diet-cola) 1단계: 필요한 부분이 남는가

4절에서 큰 모델 비용의 대부분은 읽기였습니다. 그래서 도구 출력을 줄여서 넘기는 계층(`internal/cola`)을 만들고, 먼저 가장 싼 질문부터 쟀습니다. 줄인 뒤에도 과제에 필요한 부분이 남아 있는가입니다.

방식은 다음과 같습니다.
- **블록 나누기:** 도구 출력을 블록으로 나눕니다. 코드는 함수 단위, HotpotQA는 문장 단위입니다.
- **순위 매기기:** 순위기(ranker)가 블록에 순위를 매깁니다.
- **예산만큼 남기기:** 순위대로 예산만큼 남깁니다.
- **원문 그대로 보여 주기:** 남긴 줄은 원문 그대로 보여 줍니다. 숨긴 구간은 숨긴 함수 이름을 적은 한 줄 표시로 바꾸고, 그 표시로 원문을 정확히 되살릴 수 있습니다(`expand`).

이 불변식(원문 보존, 정확한 복원, 예산 준수)은 무작위로 만든 300개 사례의 단위 테스트로 확인했습니다.

**필요한 부분을 어떻게 정했나**
- **SWE-bench:** 참조 패치가 고친 줄이 들어 있는 블록입니다. 대상은 4절의 sympy 45문제이고, 고칠 파일은 알려 줬습니다.
- **HotpotQA:** distractor 설정 검증 세트 앞 200문제의 근거 문장(supporting facts)입니다.

- **한 번 거르고 끝내는 방식은 코드에 쓸 수 없습니다.** 도구 출력이 처음 들어올 때 한 번 걸러서 넘기는 설계로는 고칠 위치를 3분의 1가량 숨기게 됩니다.
- **코드에서는 복구 경로가 필수입니다.** 숨긴 함수 이름을 표시에 남기고, 큰 모델이 `expand`로 다시 열 수 있어야 합니다. 그래서 다음 단계의 핵심 질문은 "필요한 블록이 숨겨졌을 때 Opus가 알아채고 여는가"(오류 주입 단계)입니다. 4절 조합에서도 조각이 정답 위치를 놓친 문제 중 일부는 다른 위치를 고쳐 통과했습니다. 그래서 이 표의 포함률은 성공률의 하한이 아니라, 정답 위치 하나만 기준으로 잰 보수적인 값입니다.
- **문서·검색형 출력에는 이 방식을 바로 써도 됩니다.** 근거 문장이 짧고 질문과 직접 이어지는 출력이라, Haiku가 고르는 방식이 잘 맞습니다.
- **비용:** 이 단계에 든 모델 비용은 $3.07입니다.

## 7. 읽기 압축 2단계: 실행 신호, 그리고 숨긴 코드를 다시 여는가

6절에서 남은 질문은 두 가지였습니다.
- **위치 찾기:** 모델 판단이 아닌 신호로 위치를 더 잘 찾을 수 있는가.
- **복구:** 필요한 코드가 숨겨졌을 때 큰 모델이 알아채고 다시 여는가.

조건은 6절과 같습니다(sympy 45문제, 고칠 파일은 알려 줌, 캐시 끔).

### 실행 신호: 정확하지만 좁음

이슈에 들어 있는 예제 코드를 수정 전 코드에 대해 돌리면서, 대상 파일에서 실제로 호출된 함수와 예외 traceback에 걸린 함수를 기록했습니다(`adapters/python/trace.py`). 실행은 `sandbox-exec`로 네트워크를 막고, 임시 디렉터리 밖에는 쓰지 못하게 했습니다.

- **예제 실행:** 36문제는 예제를 일부라도 실행할 수 있었습니다. 대상 파일의 함수가 하나라도 호출된 문제는 28개였습니다.
- **traceback:** 예외가 대상 파일 함수에서 난 문제는 10개였고, 그중 9개에서 traceback에 고칠 함수가 있었습니다. 신호는 정확하지만 드뭅니다.
- **Haiku의 실패는 못 메움:** Haiku가 놓친 13문제 중 실행 신호가 잡은 것은 1문제뿐입니다.
- **놓친 이유:** 13문제 중 6개는 새 함수를 추가하는 수정이었습니다(맞힌 32문제에서는 3개). 새 코드는 어느 이웃 옆에 들어가도 되므로, "정답 블록"이라는 기준 자체가 너무 엄격합니다. 기존 코드를 고치는 문제만 보면 Haiku의 지정은 29/36(81%)을 담습니다.

### 압축본을 읽어도 Opus의 판단은 같았음

다음 세 조건을 비교했습니다.
- **전체 읽기(2회):** Opus가 파일 전체를 읽습니다. 같은 조건을 두 번 돌려 Opus 자신의 흔들림을 기준선으로 삼았습니다.
- **압축본:** Haiku가 고른 블록에 예산(파일 토큰의 20%)까지 채운 화면입니다. 4천 토큰 미만 파일은 그대로 보여 줍니다. 숨긴 구간 표시에는 숨긴 함수 이름을 모두 적었고, Opus는 숨긴 함수를 두 번까지 요청할 수 있습니다.

| | 고칠 함수를 모두 지목 | 전체 읽기 1회차와 같은 답 | 문제당 비용 | Opus 입력 토큰 |
| --- | --- | --- | --- | --- |
| 전체 읽기 1회차 | 30/45 | – | $0.144 | 33,236 |
| 전체 읽기 2회차 | 30/45 | 40/45 | $0.143 | 33,237 |
| 압축본 | 30/45 | 40/45 | **$0.068** | 13,682 |

- **판단 결과가 같음:** 압축본만 맞히거나 전체 읽기만 맞힌 문제가 하나도 없었습니다.
- **차이는 잡음 수준:** 압축본과 전체 읽기의 일치(40/45)는 전체 읽기 두 번 사이의 일치(40/45)와 같습니다.
- **비용:** 53% 줄었습니다. 화면 크기는 파일 추정 토큰의 중앙값 30%였습니다.
- **숨긴 코드는 한 번도 요청하지 않음:** 정답 블록이 숨겨진 9문제는 전체를 읽은 Opus도 다른 곳을 지목한 문제였습니다(9문제 중 8문제). 압축이 숨긴 것은 Opus도 고르지 않았을 곳이었습니다.
- **이름만으로 충분:** Opus는 숨긴 함수의 이름만 보고도 지목할 수 있었습니다. 위치를 정하는 데는 본문이 필요 없습니다.

### 코드가 정말 필요할 때: 오류 주입

위치 지목은 이름만으로 되니, 복구 능력을 시험하지 못합니다. 그래서 답에 수정할 줄을 **원문 그대로 한 줄 인용**하게 했습니다. 이건 본문을 봐야만 할 수 있습니다. 오류 주입 조건에서는 전체 읽기 1회차가 지목한 함수를 일부러 숨겼습니다.

| | 숨긴 코드를 요청 | 인용한 줄이 보여 준 부분에 있음 | 보지 않은 줄을 인용 | 전체 읽기와 같은 답 | 문제당 비용 |
| --- | --- | --- | --- | --- | --- |
| 압축본(+인용) | 4/45 | 45/45 | 0 | 37/45 | $0.075 |
| 오류 주입(+인용) | 32/45 (31개는 숨긴 답을 정확히 요청) | 37/45 | **8** | 36/45 | $0.111 |

- **보통은 다시 엶:** 필요한 코드가 숨겨지면 Opus는 71%(32/45) 경우에 그 코드를 요청했습니다. 요청한 32문제는 모두 보여 준 코드에서 인용했습니다.
- **나머지는 기억으로 답함:** 요청하지 않은 13문제 중 8개는 **보지 않은 줄을 인용**했습니다. 그런데 8줄 모두 실제 파일에 글자 그대로 있었습니다. Opus가 sympy 코드를 기억하고 있다는 뜻입니다(예: `num[1] = long(num[1], 16)`).
- **공개 저장소라서 부풀려진 결과:** 학습 데이터에 없는 비공개 코드였다면 이 8개는 지어낸 인용이 됐을 것입니다. sympy 같은 공개 저장소의 결과는 기억 때문에 실제보다 좋게 나옵니다.
- **기계적으로 막을 수 있음:** "보지 않은 줄을 인용했는가"는 문자열 비교로 확인할 수 있습니다. 아래의 인용 관문이 이 8개를 처리합니다.

### 인용 관문

인용 관문(`cola.CheckQuote`)은 답이 인용한 줄이 보여 준 화면에 있는지 문자열로 확인합니다. 없으면 두 가지를 펼쳐 보여 준 뒤 다시 묻습니다(최대 2회).
- 그 줄이 들어 있는 숨긴 블록
- 답이 지목했는데 숨겨져 있던 함수

오류 주입 조건 그대로(전체 읽기가 지목한 함수를 숨김) 45문제를 다시 돌렸습니다.

| | 보지 않은 줄을 인용한 채 끝남 | 인용한 줄이 정답 블록에 있음 | 고칠 함수를 모두 지목 | 문제당 비용 | Opus 호출 수 |
| --- | --- | --- | --- | --- | --- |
| 오류 주입, 관문 없음 | 8/45 | 36 | 28/45 | $0.111 | 1.71 |
| 오류 주입, 관문 있음 | **0/45** | 39 | **30/45** | $0.123 | 1.87 |
| 전체 읽기 | – | – | 30/45 | $0.144 | 1.00 |

- **보지 않은 코드 인용이 사라짐:** 관문이 발동한 문제는 4개였고, 모두 펼친 뒤 보여 준 코드에서 다시 인용했습니다. 이 중 3개는 정답 블록의 줄이었습니다.
- **스스로 요청한 경우:** Opus가 스스로 요청한 문제는 35개로, 관문 없는 실행(32개)보다 조금 많았습니다. 같은 조건에서도 실행마다 이 정도는 흔들립니다.
- **최악의 조건에서도 더 쌈:** 필요한 코드를 일부러 숨긴 최악의 조건에서도, 결과는 전체 읽기와 같고(30/45) 비용은 15% 적었습니다. 자연스러운 압축 조건(위 표의 압축본)에서는 비용이 절반 가까이 줄었습니다($0.075, 인용 포함).
- **비용:** 이 실행에 든 모델 비용은 $5.53입니다.

### 의미

- **위치 찾기에는 압축이 안전함:** 블록 이름을 남긴 압축본으로 위치를 정하면 판단은 그대로이고 비용은 절반입니다. 6절의 "필요한 함수가 3분의 1 숨겨짐"은 대부분 Opus도 고르지 않았을 곳이었고, 새 함수를 추가하는 문제에서는 기준이 엄격했던 탓입니다.
- **코드 본문이 필요할 때는 관문이 필요함:** 다시 여는 경로는 70% 정도 스스로 작동합니다. 나머지는 인용 관문이 강제로 복구했습니다. 관문을 둔 뒤에는 보지 않은 코드를 인용한 답이 남지 않았습니다.
- **평가는 공개 코드 밖에서 해야 함:** 기억 효과 때문에, 이 방식의 평가는 공개 저장소 밖(새 이슈나 비공개 코드)에서 해야 합니다.
- **비용:** 이 절에 든 모델 비용은 인용 관문 실행을 포함해 $29.88입니다.

## 8. 읽기 압축 3단계: 실제 수정까지

7절까지는 위치 지목과 한 줄 인용만 쟀습니다. 이번에는 diet-cola 화면을 실제 수정 흐름에 넣고, 숨은 테스트로 통과 여부를 쟀습니다. 조건은 같은 sympy 45문제, 고칠 파일은 알려 줌, 캐시 끔입니다.

새 조건은 둘입니다.
- `large-cola`: Opus가 diet-cola 화면을 읽고 직접 수정합니다. 화면은 Haiku가 고른 블록에 파일 토큰 20% 예산까지 채우고, 4천 토큰 미만 파일은 통째로 보여 줍니다. 숨긴 구간 표시에는 함수 이름을 모두 적었습니다. Opus는 숨긴 함수를 두 번까지 요청할 수 있습니다. 인용 관문은 수정의 `search` 문구에 적용했습니다. 파일에는 있지만 보여 주지 않은 줄을 `search`에 쓰면, 그 블록을 펼치고 다시 묻습니다.
- `large-colaarch`: 같은 화면을 Opus가 읽고 80단어 이내의 지시와 고칠 줄 하나의 인용(관문 적용)을 씁니다. 수정은 Haiku가 같은 화면을 보고 합니다.

| --- | --- | --- | --- | --- |
| Opus 단독 (파일 전체) | 34/45 (76%) | $0.125 | 25,404 | – |

| **diet-cola, Opus 편집** | **36/45 (80%)** | $0.082 | 12,646 | 3 / 1, p=0.62 |
| diet-cola, Opus 지시와 Haiku 편집 | 32/45 (71%) | $0.074 | 12,166 | 2 / 4, p=0.69 |

- **Opus 편집: 통과는 그대로, 비용은 35% 감소.** diet-cola 화면을 읽고 Opus가 직접 고치면 36/45로, Opus 단독(34/45)보다 낮지 않았습니다. 비용은 35% 줄었습니다. 차이는 통계적으로 구분되지 않습니다(p=0.62). 그러니 "같은 수준"으로 읽어야 합니다.
- **편집을 Haiku에 넘겨도 거의 아끼지 못함.** Opus가 지시만 쓰고 Haiku가 고치게 해도 Opus 비용은 $0.079에서 $0.069로 $0.01밖에 줄지 않았습니다. 통과는 4문제 줄었습니다. 읽기를 줄이고 나면, 큰 모델 비용에서 수정을 쓰는 몫은 작습니다. 4절의 "비용 대부분은 읽기"와 같은 결론입니다.
- **v2 조합과의 관계.** v2는 Haiku가 고른 함수만 담은 조각(Opus 입력 약 5,800토큰)을 Opus가 읽어 가장 쌉니다. diet-cola 화면은 그보다 크고(파일 토큰 중앙값 30%, 숨긴 함수 이름 목록 포함) 두 배 가까이 비싸지만, 통과는 4문제 많았습니다. 세 조건은 비용과 통과의 맞교환 위에 있습니다: v2(71%, $0.045), diet-cola(80%, $0.082), Opus 단독(76%, $0.125).
- **화면에 정답 위치가 없어도 통과.** 화면에 참조 패치 위치가 없던 9문제 중 7문제를 통과했습니다(Opus 단독은 같은 9문제에서 5문제). 화면에 정답 위치가 있던 36문제에서는 Opus 단독과 같은 29문제를 통과했습니다.
- **관문은 발동하지 않음.** 자연스러운 압축 조건에서는 인용 관문이 한 번도 발동하지 않았습니다. Opus가 숨긴 함수를 스스로 요청한 문제는 3개였고, 수정 적용 실패나 모델 오류는 없었습니다. 관문은 7절의 오류 주입처럼 필요한 코드가 숨겨졌을 때를 위한 안전장치입니다.
- **비용:** 이 절에 든 모델 비용은 $7.01입니다.

한계:
- sympy 한 저장소의 45문제이고, 고칠 파일은 알려 줬습니다.
- 각 조건을 한 번씩만 돌렸고, 비교 대상은 다른 날 돌린 결과입니다.
- 공개 저장소라서 Opus의 기억 효과가 섞여 있습니다(7절).
- 실제 에이전트처럼 여러 파일을 탐색하는 상황은 아직 재지 않았습니다.

## 9. 읽기 압축 4단계: 실제 에이전트 루프

8절까지는 고칠 파일을 알려 주고 한 번 호출로 쟀습니다. 실제 에이전트는 파일을 직접 찾고, 여러 턴에 걸쳐 도구를 부르며, 캐시를 씁니다. 이번에는 Opus를 Claude Code 에이전트(`claude -p`)로 돌렸습니다. 조건은 같은 sympy 45문제, 고칠 파일은 알려 주지 않음, 캐시 켬, 코드 실행 불가입니다.

두 조건은 도구가 같고 `read_file`이 돌려주는 내용만 다릅니다. 파일 도구는 `cmd/colamcp` MCP 서버가 제공하고, 검색은 내장 Grep과 Glob을 씁니다.
- `agent-full`: `read_file`이 파일 전체를 돌려줍니다.
- `agent-cola`: `read_file`이 diet-cola 화면을 돌려줍니다(8절과 같은 설정, Haiku 순위). 숨긴 코드는 `show`로 함수 이름이나 줄 범위를 지정해 엽니다. `edit`의 `search`에 보여 주지 않은 줄이 있으면 적용하지 않고 그 블록을 보여 줍니다(인용 관문).

| 조건 | 통과 | 문제당 비용 (중앙값) | 턴 | Opus 캐시 쓰기 / 읽기 / 출력 토큰 |
| --- | --- | --- | --- | --- |
| agent-full | 33/45 (73%) | **$0.108** ($0.069) | 5.9 | 8,034 / 47,227 / 1,691 |
| agent-cola | 34/45 (76%) | $0.147 ($0.086) | 6.3 | 10,074 / 71,737 / 2,483 |

- **에이전트 루프에서는 diet-cola가 오히려 36% 비쌌습니다.** 통과는 34 대 33으로 구분되지 않고(이 조건만 2 / full만 1, p=1.00), cola가 더 싼 문제는 45개 중 12개였습니다.
- **에이전트는 이미 스스로 압축해서 읽습니다.** full 조건의 에이전트는 문제당 `read_file`을 0.73번만 불렀습니다. 22문제에서는 파일을 한 번도 읽지 않고, Grep 결과에 나온 줄만 보고 바로 고쳤습니다. 8절의 "큰 모델 비용 대부분은 파일 읽기"는 파일 전체를 프롬프트에 넣는 호출 방식에서 생긴 비용이었습니다. 검색으로 위치를 찾는 에이전트에는 그만큼의 읽기 비용이 처음부터 없습니다.
- **캐시가 남은 읽기 비용도 줄입니다.** 읽은 파일은 한 번 캐시에 쓰이고, 이후 턴에서는 캐시 읽기 요금으로 다시 보내집니다. diet-cola가 줄이는 것은 그 한 번의 쓰기 비용입니다. 대신 `show` 호출(문제당 1.04번)과 관문으로 생긴 턴이 늘고, 턴마다 전체 기록이 다시 캐시 읽기로 청구됩니다. 출력 토큰도 47% 늘었습니다.
- **관문은 22문제에서 발동했고, 대부분 비용만 늘렸습니다.** Grep 결과로 본 줄은 MCP 서버가 모르기 때문에 "보여 주지 않은 줄"로 판정됩니다. 관문이 발동한 22문제에서 cola는 $0.133, full은 $0.076였고 통과는 17 대 17로 같았습니다. 관문이 발동하지 않은 23문제에서도 cola가 더 비쌌습니다($0.159 대 $0.137).
- **파일 전체를 읽은 문제에서도 더 쌌던 것은 아닙니다.** full 에이전트가 `read_file`을 쓴 23문제에서 cola는 $0.196, full은 $0.153이었습니다.
- **참고: 한 번 호출 방식과 비교.** 파일을 알려 주고 한 번에 고치는 8절 조건은 Opus 단독 34/45 $0.125, diet-cola 36/45 $0.082였습니다. 파일을 모르는 에이전트 full 조건(33/45, $0.108)은 그보다 크게 나쁘지 않았습니다. 다만 8절은 캐시를 껐고, 이 절은 켰습니다.
- **비용:** 이 절에 든 모델 비용은 $11.44입니다.

의미:
- diet-cola는 "파일을 통째로 프롬프트에 넣는" 파이프라인(8절)에서는 효과가 있었습니다. 하지만 검색 도구와 캐시를 쓰는 에이전트에 읽기 도구로 끼우면 효과가 없거나 손해였습니다. 이 형태 그대로는 범용 에이전트 비용 절감 도구가 아닙니다.
- 에이전트의 비용은 읽기보다 턴 수, 그리고 매 턴 다시 보내는 기록에서 나옵니다. 다음에 줄일 대상은 턴과 기록입니다. 예를 들어 오래된 도구 결과를 기록에서 줄이거나, 관문이 Grep으로 본 줄도 본 것으로 치게 할 수 있습니다.

한계:
- sympy 45문제, 조건마다 한 번씩입니다.
- 에이전트는 코드를 실행할 수 없었습니다.
- 에이전트의 턴이 평균 6번으로 짧습니다. 기록이 길어지는 큰 작업에서는 결과가 다를 수 있습니다.

## 10. 에이전트 루프에서 일 나누기: Haiku 정찰, Haiku 단독

9절 조건(파일 모름, 캐시 켬, 코드 실행 불가)에 두 조건을 더했습니다.
- `agent-haiku`: Haiku 혼자 같은 도구로 고칩니다.
- `agent-scout`: Haiku가 읽기 전용 도구(Grep, Glob, `read_file`)로 탐색하고, 관련 파일과 함수, 줄 번호, 코드 인용(150줄 이내), 원인 추정을 담은 브리핑을 씁니다. Opus는 이슈와 브리핑을 받고 `agent-full`과 같은 도구로 고칩니다. 브리핑은 "틀릴 수 있으니 기대는 부분은 확인하라"는 말과 함께 줍니다.

| 조건 | 통과 | 문제당 비용 (중앙값) | Opus 턴 | Opus 비용 |
| --- | --- | --- | --- | --- |
| agent-full (Opus 단독) | 33/45 (73%) | $0.108 ($0.069) | 5.9 | $0.108 |
| agent-scout (Haiku 정찰, Opus 수정) | 33/45 (73%) | $0.164 ($0.101) | 5.8 | $0.158 |
| agent-haiku (Haiku 단독) | 22/45 (49%) | **$0.015** ($0.005) | – | – |
| agent-cola (9절) | 34/45 (76%) | $0.147 ($0.086) | 6.3 | $0.145 |

- **Haiku 정찰은 Opus의 일을 줄이지 못했습니다.** 정찰 비용은 문제당 $0.0065로 작았고, 브리핑은 평균 878토큰이었습니다. 정찰 조건에서 Opus가 고칠 파일을 모두 본 경우는 43/45로, full 조건의 21/45보다 많았습니다. 그러나 Opus의 턴은 5.8로 그대로였습니다. `read_file`은 0.73번에서 1.07번으로 오히려 늘었습니다. 브리핑이 가리킨 파일을 Opus가 직접 다시 확인한 것입니다. 브리핑이 더해진 기록이 매 턴 다시 청구되어 Opus 비용은 47% 늘었습니다. 통과는 33 대 33으로 같았습니다(이 조건만 3 / full만 3).
- **Haiku 단독은 7분의 1 비용에 통과가 24%p 낮습니다.** Haiku는 평균 11.6턴, Grep 7.8번으로 Opus보다 훨씬 많이 헤맸지만 단가가 낮아 문제당 $0.015였습니다. Haiku가 푼 22문제 중 21문제는 Opus도 풀었습니다. Opus만 푼 문제는 12개였습니다(p<0.01).
- **에이전트 루프에서 Opus의 비용은 정보 부족이 아니라 확인과 판단에서 나옵니다.** 브리핑을 줘도 Opus는 비슷한 턴 수로 스스로 확인했습니다. 9절의 diet-cola처럼 읽을 거리를 줄이는 방법도, 이 절처럼 미리 찾아 주는 방법도 Opus의 턴을 줄이지 못했습니다. 남은 지렛대는 모델 자체를 바꾸는 쪽입니다. 예를 들어 문제를 Haiku와 Opus 중 누구에게 줄지 고르거나, Opus의 추론량을 줄이는 방법입니다.
- **비용:** 이 절에 든 모델 비용은 $8.08입니다.

한계: 9절과 같습니다. 정찰 브리핑의 형식은 하나만 시험했습니다. 예를 들어 "브리핑을 믿고 다시 읽지 말라"고 지시하면 결과가 다를 수 있습니다.

## 11. 에이전트 루프에서 모델과 추론량 고르기

9절과 10절에서 Opus에게 읽을 거리를 줄여 주거나 미리 찾아 줘도, Opus의 턴은 줄지 않았습니다. 그래서 같은 에이전트 조건(파일 모름, 캐시 켬, 코드 실행 불가)에서 모델과 추론량 자체를 바꿨습니다.
- `agent-low`, `agent-medium`: Opus를 `--effort low`, `--effort medium`으로 돌립니다. `agent-full`은 effort를 지정하지 않은 기본값입니다.
- `agent-sonnet`: 중간 크기 모델인 Sonnet 5.5(`claude-sonnet-5-5`)로 돌립니다.

| 조건 | 통과 | 문제당 비용 (중앙값) | 턴 | Opus 기본값 대비 (이 조건만 / 기본값만) |
| --- | --- | --- | --- | --- |
| Opus 기본값 (agent-full) | 33/45 (73%) | $0.108 ($0.069) | 5.9 | – |
| Opus medium | 33/45 (73%) | $0.117 ($0.059) | 6.2 | 1 / 1, p=1.00 |
| **Opus low** | 30/45 (67%) | **$0.073** ($0.045) | 4.7 | 0 / 3, p=0.25 |
| Sonnet 5.5 | 23/45 (51%) | $0.072 ($0.041) | 8.1 | 1 / 11, p=0.01 |
| Haiku 단독 (10절) | 22/45 (49%) | $0.015 ($0.005) | 11.6 | 1 / 12, p<0.01 |

- **Opus low: 비용 32% 감소, 통과 3문제 감소.** 턴이 5.9에서 4.7로, 출력 토큰이 1,691에서 1,123으로 줄었습니다. low가 푼 30문제는 모두 기본값도 푼 문제였습니다. 차이는 통계적으로 구분되지 않지만(p=0.25), 방향은 일관되게 손해입니다.
- **Opus medium은 기본값과 비용·통과가 같았습니다.** 기본값이 medium에 가까운 것으로 보입니다.
- **Sonnet은 Opus low와 비용이 같고 통과는 7문제 적었습니다.** 턴이 8.1로 더 많아, 단가가 낮은 이점이 사라졌습니다. 이 과제에서 Sonnet은 Opus low에 비해 나을 게 없습니다.
- **Haiku 먼저, 실패하면 Opus로 넘기기도 Opus low보다 나쁩니다.** 모델의 통과 판정은 믿을 수 없으므로(요약), Haiku의 행동을 넘김 신호로 써 봤습니다. 턴 수가 많거나 수정이 없으면 넘기는 규칙입니다. 문턱을 사후에 골라도 가장 좋은 경우가 28/45 $0.086이었고, Opus low 단독(30/45 $0.073)보다 통과는 적고 비용은 많았습니다. Haiku가 푼 문제와 못 푼 문제의 턴 수 중앙값은 6 대 8로 겹쳤습니다. 이상적인 넘김(Haiku가 실제로 푼 문제만 Haiku에 맡김)이라면 34/45에 약 $0.07이지만, 그 판별을 해 줄 신호가 없습니다.
- **정리하면, 이 45문제에서 쓸 만한 선택지는 세 개입니다.** Haiku 단독(49%, $0.015), Opus low(67%, $0.073), Opus 기본값(73%, $0.108). 나머지 조건(diet-cola, Haiku 정찰, Sonnet, Opus medium, 턴 수 넘김)은 이 셋 중 하나보다 통과는 같거나 낮고 비용은 같거나 높았습니다.
- **비용:** 이 절에 든 모델 비용은 $11.79입니다.

한계: 9절과 같습니다. Opus low와 기본값의 3문제 차이는 실행 간 흔들림(±3문제)과 같은 크기입니다.

| 큰 모델이 "다른 함수가 필요하다"고 요청 | 3번 발동해 1번 통과. 다른 파일을 요청하는 경우가 있었음 |

## 한계

- SWE-bench 실험은 sympy 한 저장소의 45문제입니다. 조건마다 한 번씩만 돌렸습니다.
- 수정할 파일은 8절까지 미리 알려 준 조건입니다. 파일을 직접 찾는 에이전트는 9절에서만 쟀습니다.
- 조합은 25문제에서 정했습니다. 새 20문제에서는 Opus 단독보다 2문제 적게 통과했습니다.
- SWE-bench Lite에는 이슈만으로 기대 출력이 정해지지 않는 문제가 섞여 있습니다. 숨은 테스트를 보여 준 조건의 91%는 실제로는 얻을 수 없는 상한입니다.
- Polyglot에서 Opus가 테스트를 보지 않고도 99%를 낸 데에는 공개된 Exercism 테스트 관례를 알고 있는 영향이 있을 수 있습니다.
- 결정 모델은 실제 토큰 확률을 주는 모델이 아니라 Haiku의 자기 보고 확신도로 대신했습니다.

## 재현

```bash
go build -o bin/polybench ./cmd/polybench

# Polyglot (1절)
bin/polybench run -langs go,java,python,javascript -arms small,large,graybox -threshold 0.5 -out full.jsonl
bin/polybench summary full.jsonl

# Polyglot, Haiku가 실패한 문제만 (2절). c5h2 = 5회 시도 후 힌트, c5p = 의사코드 먼저, c2t = 테스트 공개
bin/polybench run -pairs haiku-failed.txt -arms c5h2,c2h2,c5p,c2t -out cascade.jsonl

# SWE-bench (3~5절). 먼저 문제를 내려받아 검증합니다.
python3 scripts/bench/swe_validate.py ~/bench-data/swe ~/bench-data/swe/venv39/bin/python
export DISABLE_PROMPT_CACHING=1
bin/polybench swe -ids ids.txt -inst-dir ~/bench-data/swe/inst -repos-dir ~/bench-data/swe/repos \
  -python ~/bench-data/swe/venv39/bin/python \
  -arms small,small-ctx,small-tdd,small-oracle,large,large-hslice,large-hleanarch2,small-locate -out swe.jsonl
```

SWE-bench 조건 이름은 `<수정 모델>-<방식>`입니다.

| 방식 | 뜻 |
| --- | --- |
| `ctx`, `tdd`, `oracle` | 기존 테스트 공개, 재현 테스트를 직접 작성, 숨은 테스트 공개 |
| `stest`, `ltest` | 작은 모델, 큰 모델이 이슈만 보고 테스트를 작성 |
| `oslice`, `hslice` | 참조 패치 기준 조각, Haiku가 고른 조각 |
| `hlean`, `harch`, `hleanarch` | 개요 제거, 지시만 쓰고 Haiku가 편집, 둘 다 |
| `hleanarch2` | 위에 더해 큰 모델이 다른 함수를 한 번 요청할 수 있음 |
| `locate` | 위치 찾기와 조각 만들기만 |
| `cola`, `colaarch` | diet-cola 화면을 읽고 큰 모델이 직접 편집, 큰 모델은 지시만 쓰고 Haiku가 편집 (8절) |

에이전트 조건 `agent-full`, `agent-cola`는 Opus를 Claude Code 에이전트로 돌리고, `read_file`이 전체 파일이나 diet-cola 화면을 돌려줍니다(9절). `agent-haiku`는 Haiku 단독, `agent-scout`는 Haiku가 탐색해 브리핑을 쓰고 Opus가 고칩니다(10절). `agent-low`, `agent-medium`은 Opus의 effort를 낮추고, `agent-sonnet`은 Sonnet 5.5로 돌립니다(11절).

6절(읽기 압축)은 `cmd/colabench`로 잽니다. HotpotQA는 Hugging Face datasets server의 `rows` API로 `hotpotqa/hotpot_qa`(distractor, validation) 200행을 받아 둔 디렉터리를 씁니다.

```bash
go build -o bin/colabench ./cmd/colabench
bin/colabench swe -inst-dir ~/bench-data/swe/inst -repos-dir ~/bench-data/swe/repos \
  -rankers head,random,lexical,haiku,haiku-wide,haiku-x3,opus-outline -out cola_swe.jsonl
bin/colabench hotpot -data ~/bench-data/hotpot -n 200 -rankers head,random,lexical,haiku -out cola_hotpot.jsonl
python3 scripts/bench/cola_report.py cola_swe.jsonl cola_hotpot.jsonl

# 7절: 실행 신호(예제를 sandbox-exec 안에서 실행), 압축본 대 전체 읽기, 오류 주입
bin/colabench swe -inst-dir ~/bench-data/swe/inst -repos-dir ~/bench-data/swe/repos \
  -python ~/bench-data/swe/venv39/bin/python -rankers trace -out cola_trace.jsonl
bin/colabench recover -inst-dir ~/bench-data/swe/inst -repos-dir ~/bench-data/swe/repos -arms full,full2,cola -out recover.jsonl
bin/colabench recover -inst-dir ~/bench-data/swe/inst -repos-dir ~/bench-data/swe/repos -arms cola,inject -quote -ref recover.jsonl -out quote.jsonl
python3 scripts/bench/recover_report.py recover.jsonl
python3 scripts/bench/quote_report.py recover.jsonl quote.jsonl
bin/colabench recover -inst-dir ~/bench-data/swe/inst -repos-dir ~/bench-data/swe/repos -arms inject -quote -gate 2 -ref recover.jsonl -out gate.jsonl
python3 scripts/bench/gate_report.py recover.jsonl quote.jsonl gate.jsonl

# 8절: diet-cola 화면으로 실제 수정
bin/polybench swe -ids ids.txt -inst-dir ~/bench-data/swe/inst -repos-dir ~/bench-data/swe/repos \
  -python ~/bench-data/swe/venv39/bin/python -arms large-cola,large-colaarch -out swe-cola.jsonl
python3 scripts/bench/cola_e2e_report.py swe-cola.jsonl swe-opus.jsonl swe-holdout.jsonl swe-v2.jsonl

# 9절: 에이전트 루프 (캐시 켬)
go build -o bin/colamcp ./cmd/colamcp
unset DISABLE_PROMPT_CACHING
bin/polybench swe -ids ids.txt -inst-dir ~/bench-data/swe/inst -repos-dir ~/bench-data/swe/repos \
  -python ~/bench-data/swe/venv39/bin/python -arms agent-full,agent-cola,agent-haiku,agent-scout,agent-low,agent-medium,agent-sonnet -j 4 -out swe-agent.jsonl
python3 scripts/bench/agent_report.py swe-agent.jsonl swe-opus.jsonl swe-holdout.jsonl swe-cola.jsonl
```

표를 만든 스크립트는 `scripts/bench/`에 있습니다. 원본 결과(`bench-results/*.jsonl`)는 저장소에 넣지 않았습니다.
